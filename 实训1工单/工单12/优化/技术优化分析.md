## 一、优化目标

本工单核心目标：**引入LightRAG知识图谱架构，与传统RAG混合检索架构进行系统性对比评估**，验证知识图谱在招股说明书问答场景下的优势与局限。

---

## 二、架构对比分析

### 2.1 传统RAG架构

```
用户问题 → 查询理解 → 向量检索(bge-m3) + BM25(jieba) → RRF融合 → Reranker重排 → LLM生成
```

| 组件 | 技术栈 | 作用 |
|------|--------|------|
| 向量检索 | Milvus + bge-m3 (1024维) | 语义相似度召回 |
| 全文检索 | BM25 + jieba分词 | 关键词精确匹配 |
| 融合排序 | RRF (k=60) | 多路结果归一化融合 |
| 重排序 | bge-reranker-v2-m3 | 交叉编码器精细打分 |
| 生成 | DeepSeek-chat API | 基于上下文生成答案 |

**优点：** 检索速度快（平均0.21s），数字精确度高  
**缺点：** 语义理解浅，实体关系检索弱，上下文容易混入无关内容

### 2.2 LightRAG知识图谱架构

```
用户问题 → 关键词提取 → 知识图谱检索(hybrid) → LLM生成
         ↓
    ┌────────────────┐
    │ 局部检索(Local) │ ← 实体精确匹配
    │ 全局检索(Global)│ ← 关系推理遍历
    │    融合(Hybrid) │
    └────────────────┘
```

| 组件 | 技术栈 | 作用 |
|------|--------|------|
| 实体抽取 | DeepSeek LLM | 从文档中提取实体和关系 |
| 图存储 | GraphML + nano-vectordb | 结构化知识表示 |
| 检索 | hybrid模式（局部+全局） | 实体匹配 + 关系推理 |
| 嵌入 | bge-m3 (1024维) | 实体/关系向量化 |
| 生成 | DeepSeek-chat API | 基于图谱上下文生成答案 |

**优点：** 语义理解深，实体关系精确，答案完整性高  
**缺点：** 首次构建耗时长，查询速度较慢（平均4.37s）

### 2.3 架构差异总结

| 维度 | 传统RAG | LightRAG |
|------|---------|----------|
| 知识表示 | 文本块（扁平） | 实体-关系-实体（图结构） |
| 检索方式 | 向量相似度 + 关键词 | 图遍历 + 向量匹配 |
| 语义深度 | 浅层（词向量距离） | 深层（关系推理） |
| 上下文质量 | 易混入无关内容 | 精确匹配实体关系 |
| 构建成本 | 低（直接分块入库） | 高（LLM抽取实体关系） |
| 查询速度 | 快（~0.2s） | 慢（~4.4s，含LLM推理） |

## 三、关键技术优化

### 3.1 知识图谱构建优化

#### 优化点1：分文档独立存储
```
问题：两份招股书混合存储导致检索混淆
方案：兴图新科 → lightrag_storage_v2/，力源信息 → lightrag_storage_ly/
效果：查询时根据关键词自动路由到对应知识图谱
```

#### 优化点2：chunk_token_size调优
```
问题：默认chunk过小导致实体关系断裂
方案：chunk_token_size=3000, chunk_overlap_token_size=200
效果：保持实体-关系的完整性，减少信息碎片化
```

#### 优化点3：异步LLM函数
```python
# 错误写法（同步函数会导致await报错）
def llm_func(prompt, **kw):
    return call_api(prompt)

# 正确写法（异步函数）
async def llm_func(prompt, system_prompt='', **kw):
    return call_api(prompt)
```

### 3.2 查询路由优化

#### 优化点：关键词自动路由
```python
def classify_question(question):
    for kw in ['力源信息', '力源信息技术', '武汉力源']:
        if kw in question:
            return 'ly'  # → lightrag_storage_ly
    return 'xt'          # → lightrag_storage_v2
```

**效果：** 用户无需手动选择知识图谱，系统根据问题关键词自动路由。

### 3.3 事件循环冲突解决

#### 问题
lightrag-hku 1.1.7的`__post_init__`在async上下文中调用`run_until_complete`，与`asyncio.run()`冲突。

#### 解决方案
```python
import nest_asyncio
nest_asyncio.apply()  # 允许嵌套事件循环
```

**效果：** 在已有事件循环的环境中正常运行LightRAG查询。

### 3.4 RAGAS评分优化

#### 优化点1：评分Prompt标准化
```python
def score_rag(question, answer, context):
```

```python
# 对RAG得分为0的题自动重新检索
```

### 4.3 关键发现

#### 发现1：实体关系类问题提升最大
提升≥0.55的8道题全部涉及实体关系检索：
- 组织架构（ID 5）：销售部→大客户销售部→销售处
- 技术标准（ID 95）：兴图新科→参与制定→标准
- 获奖信息（ID 795）：兴图新科→参与→C4ISR工程→一等奖
- 法定代表人（ID 531）：程家明→法定代表人→公司

**结论：** 知识图谱在实体关系检索上优势显著，RAG的向量相似度难以捕捉多跳关系。

#### 发现2：RAG在数字精确问题上仍有优势
ID 260（军用收入金额）和ID 33（军用收入占比）是RAG唯二胜出的题：
- RAG检索到包含具体数字的文本块，直接引用
- LightRAG的图谱更擅长关系推理，数字定位略弱

**结论：** 对于需要精确数字引用的场景，传统RAG的文本块检索仍有价值。

#### 发现3：RAG的上下文质量问题
RAG的context_precision仅0.4688，说明检索到的上下文中约53%是无关内容。典型表现：
- 查询"法定代表人"却检索到"术语释义表"
- 查询"下游行业"却检索到"验资复核声明"

**结论：** RAG的向量+BM25检索容易被高频词汇（如公司名称）干扰，导致检索漂移。

## 八、结论

### 8.1 核心结论

1. **LightRAG在语义理解上显著优于传统RAG**：context_recall提升150%，context_precision提升110%
2. **知识图谱适合实体关系密集型场景**：组织架构、人物关系、事件关联等问题提升最大
3. **传统RAG在数字精确场景仍有价值**：具体金额、占比等数字引用更准确
4. **融合架构是最优方案**：RAG处理快速数字查询，LightRAG处理复杂语义推理

### 8.2 技术债务

| 问题 | 优先级 | 说明 |
|------|:------:|------|
| reranker兼容性 | 高 | ragas_py310环境reranker推理崩溃，需降级transformers |
| lightrag版本锁定 | 中 | 1.3.9有pipeline_status bug，锁定1.1.7 |
| 查询速度 | 中 | LightRAG平均4.37s，需优化缓存或预计算 |
| 知识图谱更新 | 低 | 当前为静态构建，需支持增量更新 |
